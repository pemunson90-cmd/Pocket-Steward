## What went in

`[pat]` Two things, from one real run on 2026-09-17: the app could not account
for what it had done, and it had flattened folders that meant something as a
unit.

`[device]` The triggering run: Smart cleanup moved 4,829 files and created 5
folders with 1 failure. A duplicate pass trashed 3,316 files. Both succeeded.
Neither could be audited afterward from inside the app, and the 4,829 files had
been pulled out of folders a human had already organised.

Constraints the work was built under:

- `[pat]` **Nothing deletes, ever.** Standing since M2. Trash is a move to
  `PocketSteward/Trash/<mirrored path>`. There is deliberately no empty-trash
  action anywhere in the app, and the M6 spec restated it: "Do not add an
  'empty trash' action. That constraint is owner policy, not an oversight."
- `[code]` **No Room schema change.** `AppDatabase` is on
  `fallbackToDestructiveMigration(dropAllTables = true)`, and the phone held
  the undo journal for the 4,829-operation run. Any new column or entity would
  have wiped it. Adding an enum *value* is safe (TypeConverter stores a
  String); adding a *column* is not.
- `[pat]` **No deferrals.** 6c was scoped as deferrable by the spec itself
  ("this is convenience; 6a and 6b are the safety") and was initially deferred.
  Pat rejected that: "No deferrals if I asked for it I want it." It was built
  in `b1f7386`.

**Cost:** two commits. 73 pure-Kotlin tests written and passing against a real
compiler in a scratch module. Neither commit was compiled in the environment
that wrote it; both were built elsewhere.

## What can't change

Each of these has a cost of breaking it, stated. Change any of them only by
paying that cost knowingly.

**1. Nothing deletes.**
`[pat]` Owner policy, not a technical limit. Trash is a move. Unprotecting a
folder trashes its marker. Undoing a written file trashes it.
*Cost of breaking:* the app stops being safe to run unattended on a phone that
holds the only copy of things. This is the reason the project exists.
*The one exception, already granted:* `removeEmptyDirectory`, which deletes an
empty directory the current task itself created, during undo of a
`CreateDirectory`. It cannot touch a directory with contents and it cannot
touch one the app did not create.

**2. The chain: intent → planner → typed manifest → validator → preview →
executor → journal.**
`[code]` Plan Decision 1. Enforced by types: a `PlanSource` returns a
`GeneratedCleanup` and cannot reach a `StorageGateway`. Proposing and executing
are different objects.
*Cost of breaking:* the AI layer arriving in M8+ gets a path to the filesystem
that no human approved. Every safety property in this app is downstream of this
ordering.

**3. `PlanValidator` runs as a whole-plan pre-pass, never interleaved with
execution.**
`[code]` Plan Section 12. `PlanExecutor` re-validates before executing, which
is why `execute` had to gain an `index` parameter when 6c introduced folders
the scan index has never seen.
*Cost of breaking:* a preview that shows one thing and an execution that does
another.

**4. Protection lives in the filesystem, not the database.**
`[code]` `POCKETSTEWARD-DO-NOT-SORT.md`. Presence is the entire signal; nothing
parses it; an empty file works.
*Cost of breaking:* a protection that a destructive migration, a reinstall, or
moving storage to another device silently removes. It is also the reason a
model can later *propose* protection without being able to weaken it: the
enforcement reads a file on disk, not a model's output.

**5. No Room schema change while the phone holds an undo journal worth
keeping.**
`[code]` `fallbackToDestructiveMigration(dropAllTables = true)`, `version = 3`.
*Cost of breaking:* every undo record on the device, silently, on first launch.
*See "what needs to go" — this is a frozen constraint, not a good design.*

**6. The keeper-path round trip is owned by exactly two functions.**
`[code]` `duplicateTrashReason` writes it, `keeperPathFrom` reads it, and they
are tested as a pair. Nothing else formats or parses that string.
*Cost of breaking:* a manifest that silently reports "not recorded" for every
trashed file, with no error anywhere.

## What needs to go

**1. `fallbackToDestructiveMigration`.**
`[code]` This is the single worst thing in the codebase. It turned a routine
schema change into a data-loss event and forced three separate workarounds in
M6 alone: the SHA in the previously-unused `sourceFingerprint` column, the
keeper path smuggled through a reason string, and `planJson` repurposed as a
tab-separated side table. Every one of those is a workaround for a decision
that should be reversed.
*Replace with:* real migrations, starting the next time a schema change is
genuinely needed. Until then, every milestone pays this tax.

**2. `planJson` as a parseable side channel.**
`[code]` It is a free-text column holding `sequence<TAB>TYPE<TAB>reason`, joined
to the journal by sequence number. It works and it is tested. It is also a
schema pretending not to be one, and it exists only because of item 1.

**3. Scope overlap in `FileRecord`.**
`[code]` `scopeRootRef` is set per scan, and `upsert` is keyed on `stableRef`.
Scanning Downloads and then a folder inside it re-scopes the shared records, so
`getFilesUnderScopeRoot` on the outer scope then misses them. Pre-existing,
predates 6c (Downloads and "Everything" already overlapped), and not observed
to have caused a wrong result yet. Not a reason to relax: it is a correctness
bug waiting for the right sequence of scans.

**4. `SafStorageGateway` is a stub that type-checks.**
`[code]` `openRead`, `createDirectory`, `move`, `rename`, `trash` and now
`writeTextFile` are all `TODO()`. The UI fences SAF mode out of every path that
would reach them, so the stub never throws in practice — which means nothing
tests that the fencing is complete. Either implement it or delete the mode.

**5. `StorageScopeScreen.kt` is 748 lines and `ScanViewModel.kt` is 872.**
`[code]` Every review screen in the app is a private composable inside one
`when`, and every one of their back handlers is `viewModel::reset`.
`[device]` The consequence, hit on hardware: opening "Files older than 6
months" and pressing back discarded a scan of 22,000 files.
*This is M7's item 1.*

**6. The extension table classifies almost nothing.**
`[device]` Roughly 13,192 of 13,700 files come back uncategorized.
`[pat]` Ruled accepted 2026-09-18 — uncategorized files are the AI layer's
input. Recorded here because "accepted" and "fine" are different words, and a
later reader should know which one this is.

## Process failures worth keeping

`[code]` **The environment that writes this code cannot compile it.**
`dl.google.com` and `maven.google.com` are blocked; `repo1.maven.org` and
`plugins.gradle.org` are reachable but rate-limited. Verification happens in a
pure-Kotlin scratch module for anything with zero Android imports, and by hand
for everything else. Every milestone through M5 shipped at least one real
compile error as a result. M6 shipped none, which is the first evidence the
scratch-module discipline is working rather than just feeling rigorous.

`[code]` **M4's `parseFileRef` failure is the pattern to watch for.** A
function existed in one tree, vanished when a different tree was swapped in,
and code was then written against the stale assumption. Static review missed it
because a private duplicate of the same logic existed elsewhere in the file. The
lesson that generalises: a hand review verifies that code is *consistent with
itself*, not that the symbols it references exist.

`[inferred]` **Deferral was wrong and got caught.** 6c was deferred on the
reasoning that the spec called it convenience. The spec's author and the owner
are the same person, and he had asked for all of it. A spec's own
prioritisation is not permission to skip the lower priority.
