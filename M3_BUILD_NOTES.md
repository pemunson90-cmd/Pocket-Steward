## Every failure encountered

Exactly one, on the first run of the supplied M3 tree.

### Failure 1 — `HistoryScreen.kt` imports a non-public declaration

`[build]` Verbatim:

```
e: file:///…/app/src/main/java/com/pocketsteward/app/ui/history/HistoryScreen.kt:9:43 Cannot access 'val RowColumnParentData?.weight: Float': it is internal in file.
```

```
* What went wrong:
Execution failed for task ':app:compileDebugKotlin'.
> A failure occurred while executing org.jetbrains.kotlin.compilerRunner.btapi.BuildToolsApiCompilationWork
   > Compilation error. See log for more details

> Task :app:compileDebugKotlin FAILED
BUILD FAILED in 1m 37s
```

`[build]` The build stopped at `compileDebugKotlin`, so `assembleDebug`
produced no artifact and `testDebugUnitTest` never ran. No APK directory, zero
test-result XML files.

`[code]` Cause: line 9 was
`import androidx.compose.foundation.layout.weight`. There is no public
top-level `weight` at that path. `weight` is a member of `ColumnScope` and
`RowScope` and is available implicitly inside a `Column` or `Row` lambda, so
it needs no import at all. The name *does* resolve at that path, to an
internal extension property on `RowColumnParentData`, which is why the
compiler reports an access violation rather than an unresolved reference.

**Fix:** delete line 9. The single usage, `modifier = Modifier.weight(1f)` at
line 92, resolves through the enclosing scope once the shadowing import is
gone. No other edit, in that file or any other.

`[inferred]` Worth flagging to whoever generates this source: this is the
second occurrence of the same mistake in consecutive rounds. Milestone 2 round
2 failed on `import androidx.compose.foundation.lazy.item` for the identical
reason — `item` is a `LazyListScope` member, not a top-level function.
`items`, `fillMaxWidth`, `fillMaxSize` and `padding` are importable because
they genuinely are top-level; `item` and `weight` are not. Two build cycles
lost to one pattern.

## Still unverified on device

**Nothing in Milestone 3 has been run on hardware.** Compiling and passing 23
JVM unit tests is not the same as the journal and undo behaving correctly
against a real filesystem. The following are all untested outside this build:

- Undo of a completed task from the immediate completion screen.
- Undo from Task History after leaving the scan flow.
- Undo after an app restart, which is the case the persistent journal exists
  for.
- Collision handling, where a newer file occupies the original path and the
  inverse is expected to block rather than overwrite.
- Removal of a created directory only when still empty.
- `MutationRecovery` at startup after a real process death mid-mutation.
- The Room 2 → 3 migration path on a device that already holds a version 2
  database. Destructive migration is configured, so the expected outcome is
  that existing scan data is wiped rather than migrated.

`[code]` The authoring session verified much of this logic in an in-memory
harness, described in `STATUS.md`. That is genuine evidence and it is not
device evidence.

## Carried forward, still open

- `[device]` The scan root is not indexed, so `PlanValidator` rejects
  `CreateDirectory` against it with "Parent directory does not exist in the
  index." Confirmed on Pat's phone at Milestone 2. `STATUS.md` describes a
  validator change this milestone around destination parents; whether that
  also resolves this specific rejection has **not** been confirmed on device.
  Worth checking first, since it is visible in one screen.
- SAF scanning has never been exercised. The `fromTreeUri` fix compiles and
  matches the library source; nobody has run it.
- Once broad access is granted there is no route in the app to choose SAF
  instead, because onboarding auto-advances.
- Bulk mutation runs still execute from the ViewModel coroutine, per
  `STATUS.md`.

## Do not "fix" these

Both are deliberate, per the person who owns the app.

`trash()` moves into `PocketSteward/Trash/<mirrored path>` and nothing in the
app ever empties it. There is no missing "empty trash" feature.

SAF mutation methods stay `TODO()`. Direct-mode mutation is the supported
path for this device and use case.
